# A1780P (F2000 with WLAN) BLE

The F2000 with WLAN (A1780P). This page owns the BLE-specific facts of the product; the command payloads (opcodes, TLV tags, scales) are owned by the MQTT page [../mqtt/a1771.md](../mqtt/a1771.md) of the product family (there is no page for this exact product) and are not repeated here. The frame, fragmentation and encryption are on [protocol.md](protocol.md), the negotiation on [handshake.md](handshake.md).

Evidence is the asm of 3.24.3 (`file.dart @0xADDR`, relative to `charging/ble/device/` unless a path is given). Pool lists such as `[0, 0x5e]` are real values. A row that says `no` in the column `on the MQTT page` means the opcode is not mentioned on the linked page; it can still be a command that also goes over MQTT.

Notes on this product:

- `A1780pAnkerDevice` extends `A1781AnkerDevice` (and mixes in `BleOtaField`), `A1780PDeviceController` extends `A1781DeviceController`; the family root is [a1771.md](a1771.md).
- This product has a parallel WiFi-and-BLE OTA page, `WifiBleParallelOtaLogic` (`charging/ui/page/device/a1780p/parallel_ota/wifi_ble_parallel_ota_logic.dart`), with the log text `BLE reconnect failed after 5 attempts, give up`; the app models both transports together for this OTA path; this does not prove simultaneous telemetry (see [protocol.md](protocol.md#connection-routing-and-the-wifi-exclusion-rule)).
- There is no MQTT page for this product.
- Negotiation, app side: `A1780pAnkerDevice` (class id 8487) has `ZXBleFeature` in its `extends` line and `A1780P` is not a registered SDK product code, so `BleHandler` picks `BleHandlerImpl1`, whose `_authDevice` starts the Dart `ZXBleConfer`. Which of the three conferers then runs depends on the capability response, not on the product ([handshake.md](handshake.md#which-implementation-runs-for-a-product)).

## Commands

### Device-class methods

#### Purpose

Lists the non-controller operations of the device class: the methods that start and end a session (connect, capability exchange, key setup, account binding, authentication, disconnect), WiFi provisioning, the OTA start and the full-status request; each method has one request opcode.

#### Upstream name

none for the sequence; the opcode names are the app's `ZXOpcodeType` members (no upstream name).

#### Opcode

Tag: asm-traced.

| method | group | opcode | site |
|---|---|---|---|
| `startBleOTA` | OTA | `002e` | a1780p_anker_device.dart @0x2848a50 |
| `sendOtaSubPackage` | OTA | `002f` | a1780p_anker_device.dart @0x36bd388 |

#### Direction

both: requests go app to device, the responses (`08xx` in the common map, [handshake.md](handshake.md#opcode-pairs)) come back device to app.

#### Packet framing

[protocol.md](protocol.md#frame-on-ble); the handshake frames carry the flag bits of [protocol.md](protocol.md#opcode-byte-0-flags).

#### Handshake prerequisite

The rows of group `handshake` are the handshake. Which conferer runs (`SecureEcdhConfer`, `EcdhConfer` or `AesConferV1`) is chosen from the capability response, not from the product: [handshake.md](handshake.md#capability-negotiation-response). The other rows are ordinary commands that need a completed handshake for encrypted frames.

#### TLV tags

The handshake payloads are positional bytes or single tags and are not per-product; they are described in [handshake.md](handshake.md#capability-negotiation-response) and [handshake.md](handshake.md#the-three-conferers). The payloads of the WiFi, OTA and status-request rows were not decoded for this page.

#### Example

none: no capture of a handshake exists in this repository.

#### Related API endpoint

none: the handshake has no MQTT twin and the product has no MQTT page.

#### Since/changed

3.18.0: the same device-class files. 3.24.3: the opcode set of the device-class file(s) is unchanged; the `ProductModel` of A1780P existed in 3.18.0 (see [protocol.md](protocol.md#since-3180)).

#### Known unknowns

none.

BLE is unavailable while the device is on WiFi; see `ble/protocol.md` (community finding, see protocol.md; not asm-traced).

### Controller send set

#### Purpose

Lists the command opcodes that the controller class of this product writes over BLE, each tied to the controller method that uses it.

#### Upstream name

none for the methods (the app's method names are used); the upstream constant for an opcode is indexed on [../mqtt/upstream_commands.md](../mqtt/upstream_commands.md).

#### Opcode

Tag: asm-traced.

| method | opcode | on the MQTT page | site |
|---|---|---|---|
| `getOTAState` | `0030` | no | a1780p_device_controller.dart @0x2418884 |
| `getOTAInfo` | `0063` | no | a1780p_device_controller.dart @0x4562f10 |
| `getOTAInfo` | `002e` | no | a1780p_device_controller.dart @0x4562f1c |
| `sendSubPackageData` | `0064` | no | a1780p_device_controller.dart @0x4613f8c |
| `sendSubPackageData` | `002f` | no | a1780p_device_controller.dart @0x4613f98 |

#### Direction

app to device for the requests; the matching responses and the periodic status push `0405` (`postDeviceAllInfoReq` in the charging map, [protocol.md](protocol.md#zx-opcode-names)) come back device to app.

#### Packet framing

[protocol.md](protocol.md#frame-on-ble) and [protocol.md](protocol.md#fragmentation); the controller's `sendCommand` waits 5 s by default ([protocol.md](protocol.md#timeouts-and-limits)).

#### Handshake prerequisite

A completed handshake is needed for encrypted commands: the frame builder encrypts only when the device has a key ([protocol.md](protocol.md#payload-encryption)).

#### TLV tags

Owned by the linked MQTT page: [../mqtt/a1771.md](../mqtt/a1771.md). Opcodes marked `no` in the table have no tag table there. Their payload shapes, read from the controller methods (shape definitions: [protocol.md](protocol.md#controller-send-wrappers)): `getOTAInfo` (`002e` or `0063`) and `sendSubPackageData` (`002f` or `0064`) take the opcode pair from `isMTU` and send the caller's map; `getOTAState` (`0030`) sends tag 0xA2 with a user-model string. The response of a request is not handled in these methods (they return Null after the send).

#### Example

none: the MQTT pages hold the synthesized frames of their products; this page adds none.

#### Related API endpoint

MQTT twin: [../mqtt/a1771.md](../mqtt/a1771.md)

#### Since/changed

3.18.0: the controller file(s) exist. 3.24.3: the opcode set is unchanged.

#### Known unknowns

- Rows marked `no` may be commands that are MQTT-only on the cloud side or simply undocumented on the MQTT page; this page does not decide which.

BLE is unavailable while the device is on WiFi; see `ble/protocol.md` (community finding, see protocol.md; not asm-traced).

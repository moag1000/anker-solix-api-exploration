# Device test backlog

This page lists the facts that a device owner can confirm or refute with one test. Every row points at the owner page that holds the fact, says what to send in a few words (the exact bodies, opcodes and tags stay on the owner page and are not repeated here), what to look for in the answer, and whether a test is already on record. It is built from the Known unknowns and Device-tested by sections of the owner pages; when those change, this page is regenerated by hand from them, it is not a second source of facts.

Pick a row, run the test, and report it as described in [../CONTRIBUTING.md](../CONTRIBUTING.md#report-a-device-tested-result). A result earns `device-tested` only when the record names client and version, device PN and firmware, date, what was sent and what was observed ([../METHODOLOGY.md](../METHODOLOGY.md#confidence-tags)). Rejections are results. Never run a test on a device or account you cannot afford to misconfigure; the output-limit and DIY-unlock rows change real settings, see [SAFE_USAGE.md](SAFE_USAGE.md).

BLE rows need the device off WiFi: BLE is unavailable while the device is on WiFi ([../ble/protocol.md](../ble/protocol.md#connection-routing-and-the-wifi-exclusion-rule)), and nothing here treats BLE as a cloud fallback.

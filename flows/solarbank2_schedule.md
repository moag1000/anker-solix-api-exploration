# Solarbank 2 schedule (param_type 6)

How the app saves the custom schedule (energy plan) of a Solarbank 2 (A17C1 family) from the energy deployment page: one of two cloud saves of the plan (the site path when the page holds a non-empty site-id string, the device path when it is empty; the branch is in step 3) and the schedule command to the device. The payloads live with their owners and are only linked here: the plan JSON on [set_site_device_param](../api/power_service/site/set_site_device_param.md) and [param_types](../api/param_types.md), the device command (opcode `005e`, tags, CRC) on [mqtt/a17c1.md](../mqtt/a17c1.md#005e-setbackpower-settacticstime-setpeakvalley). "Audit row N" counts the data rows of [../docs/audit/FLOWS.md](../docs/audit/FLOWS.md), see the [README](README.md#audit-row-numbers).

## Trigger (UI action)

On the energy deployment page the user taps the confirm control that runs the closure `energy_deploy_page.dart @0x3da9edc`, which calls `EnergyDeployLogic::sendHomeLoadData` (call at `energy_deploy_page.dart @0x3da9f08`, function `energy_deploy_logic.dart @0x2b48c8c`). The label of the control is not read from the asm. The old page claimed the entry was `ElectricityUsageHelper`; that class is not called on this path (audit row 1 names `energy_plan_logic.dart` as the sender, see the variant below).

Variant, not the main flow: deleting an entry on the energy plan page runs `EnergyPlanLogic::deleteHomeLoadData` (`energy_plan_logic.dart @0x3dac684`). It first stops with the toast `deviceOfflineConnect` (`@0x3dac800`) when the page has a device serial and its device flag (`field_7f.field_7`) is false (`@0x3dac7fc`). It then branches on the page's device-serial string (`field_7f.field_2b`, also passed to `getDeviceBySn` at `@0x3daca84`; empty test at `@0x3dac974`). With a serial it sends the device home load (`set17C1DeviceHomeLoadRes`, call at `@0x3dacb5c`) and the device command (call at `@0x3daccb0`). Without a serial it sends the same param_type 6 save as the main flow (literal `"6"` at `@0x3dacd58`, call at `@0x3dacd68`) and the device command (call at `@0x3dacf70`) only when the device status is `bleBusinessConnected`.

## Preconditions

- Network: the function stops with the toast `commonNetWorkErrorFix` when the connectivity check fails (`checkConnectivity` at `energy_deploy_logic.dart @0x2b48ccc`, text at `@0x2b48cec`, `_showNetWorkError` at `@0x2b48d00`).
- At least one repeat day: if `isPermitEditedSave` (`energy_deploy_logic.dart @0x2b48d10`) is false the page shows `a17c1RepeatPeriodEmpty` and stops (`@0x2b48d18`).
- Overlap: the page intersects the weekday sets of the other plan entries (`intersection` at `energy_deploy_logic.dart @0x2b49670`). On an overlap it shows a confirm dialog with the text `a17cxSiteHomeLoadCover` (`@0x2b499f0`, `showDialog` at `@0x2b49aac`) and returns; the confirm callback (closure `@0x2b48880`) loops twice over the plan entries (`@0x2b488d0`, `@0x2b48a78`), applies a closure to each entry's day list and then calls `sendHomeLoadData` again (`@0x2b48c28`). What the closure changes in the day lists is not read.
- The device is an A17C1-family device: `sendDeviceTacticsTime` tests the class id against four consecutive ids (`cmp x16, #3` at `energy_deploy_logic.dart @0x2b4b004`); the controller maps the four ids to the product strings `A17C1`, `A17C5`, `A17C3`, `A17C2` (`a17c1_device_controller.dart @0x226e138`, `@0x226e150`, `@0x226e168`, `@0x226e174`).

Dual-path claim of the old page ("BLE and API both sent"): the cloud save of the site path (step 4) or the home-load save of the device path (step 5) is sent in the branch that was taken, not both of them in one run; the device command (steps 6 to 8) uses exactly one transport per call, chosen at `a17c1_device_controller.dart @0x226e22c` and `@0x226e4e4`. The call from `deleteHomeLoadData` is stricter: it sends the device command only when the status is `bleBusinessConnected` (`energy_plan_logic.dart @0x3dacda4` to `@0x3dacdb0`; the compared pool object is `pp+0xca68`, member `bleBusinessConnected`). BLE is not a live fallback for a device that is on WiFi, see [ble/protocol.md](../ble/protocol.md#connection-routing-and-the-wifi-exclusion-rule).

## Side effects

- The loading overlay stays up until the callbacks of the cloud save run (`showLoading` argument at `energy_deploy_logic.dart @0x2b4adb4`). Success callback of step 4 (closure `@0x2b4b61c`, size 0x5f0): it calls `setDeviceHomeLoadSelectIndex` with the selected index from the page state (`@0x2b4b740`), fires the UI message 2100 with data true (raw 64-bit store at `@0x2b4b774`), calls `PowerUsageScenarioLogic::getHomeLoad` (`@0x2b4b7cc`); when the device's status equals `bleBusinessConnected` (`pp+0xca68`, `@0x2b4b824` to `@0x2b4b830`) it calls `sendDeviceTacticsTime` (`@0x2b4b854`, so on the site path the device command goes out from this callback and only for a BLE-connected device), otherwise it takes the device list of `StationEnergySystemLogic` (if registered and non-empty, `@0x2b4b86c` to `@0x2b4b8e8`), looks the device up again by serial (`getDeviceBySn`, `@0x2b4b9b8`), stores it in the page (`@0x2b4b9c0`) and tests the status once more for the same call (`@0x2b4ba30` to `@0x2b4ba60`); it then sends the analytics events `APP_DEVICE_CUSTOM_SET_PERIOD_CHOOSE` and `APP_DEVICE_USER_SET_PERIOD_POWER_CHOOSE` (`@0x2b4bb20`, `@0x2b4bb88`) and calls `handleEnergyPlanLogic` with a closure (`@0x2b4bbe4`). Failure callback: the `fail` argument is the shared closure `@0x2745960` (compiled once for several pages), which dismisses the loading overlay (`GetExtension.dismiss`, `@0x2745994`) and shows the message string as a toast (`show`, `@0x27459a0`).
- `sendDeviceTacticsTime` rewrites the plan-mode state (`field_7` of the mode object) before the send (`energy_deploy_logic.dart @0x2b4b088`, `@0x2b4b0bc`, `@0x2b4b0ec`).

## Timing (delays/polling)

No `Future.delayed` or timer is in `sendHomeLoadData`, `saveHomeLoadData` or `sendDeviceTacticsTime`. On the device path the sends of steps 5 to 7 are issued one after the other without awaiting an answer (`saveHomeLoadData` is not `async`, `energy_deploy_logic.dart @0x2b4ab74`); on the site path the device command is issued from the success callback of step 4. A BLE frame longer than 200 bytes (`cmp x2, #0xc8` at `a17c1_device_controller.dart @0x226e2b0`) is split when the `mtu` argument is non-zero (`cbz x0` at `@0x226e3ec`, as it is for `setTacticsTime`), and the fragments are written with a delay between them, see [ble/protocol.md](../ble/protocol.md#timeouts-and-limits).

## Failure paths

- No network: toast, nothing sent (Preconditions).
- No repeat day: toast `a17c1RepeatPeriodEmpty`, nothing sent.
- Cloud errors: the `fail` callback of step 4 is the shared closure `@0x2745960` described in Side effects: the overlay is dismissed and the message is shown; no device command is built. Error codes: [errors](../api/errors.md).
- Device not connected over BLE or WiFi: the command of step 7 is dropped without a message at this level (`a17c1_device_controller.dart @0x226e238`).

## Since/changed

Corrections of the old FLOWS.md (audit rows in brackets), with the value the old page gave:

- The cloud request does not use the old `cmd` value 246 (raw immediate); the decoded value is on param_types (rows 1, 2, 67). "Both values work" is not an asm fact.
- The schedule command has 29 data tags `a2` to `be`, not 30 tags `a2` to `bb` (row 4); the last tag is the CRC32 under `fd`, not a timestamp (rows 5, 6) and not tag 506 (row 9).
- `mtu` is 200, not 400 (row 7); the default 200 is the same value (row 8).
- Seven slots, not 14 (row 11); the 14 `intToList(0)` calls at the start of the builder are zero defaults.
- `setTacticsTime` is 13,536 bytes (header size `0x34e0`) in 3.24.3 and was 14,020 bytes (`0x36c4`) in 3.18.0 (row 10).
- The old "dual path, both sent" is replaced by the gate in step 8.

Rows consumed without change: 3 (opcode `005e`), 14 (`mode_type` 3 is `ModeTypeCustom`, owner [param_types](../api/param_types.md)), 15 (worked example, not from asm).

- The schedule enable condition of the old page (`NOT (is_charge_priority AND secondary flag)`) was not re-traced. — traced 2026-10-20: the file `energy_deploy_logic.dart` contains no string or call with `charge_priority` (grep 0), and `saveHomeLoadData` and its success callback (`@0x2b4ab74`, `@0x2b4b61c`) test none by name; a test by field offset was not ruled out.

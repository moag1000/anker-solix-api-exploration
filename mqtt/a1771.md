# A1771 MQTT commands (F1200)

SOLIX F1200 (A1771, Bluetooth and WLAN): the 0405 status message. A1753 (C800) extends the same parser chain and is on [a1753.md](a1753.md); the PPS setters of the PPS products are on [a172x.md](a172x.md). The envelope, topics, frame layout and data type codes are owned by [envelope.md](envelope.md) and are not repeated here.

Evidence rows are written `audit row N` and refer to [../docs/audit/BLE_COMMAND_MAP.md](../docs/audit/BLE_COMMAND_MAP.md); `file.dart @0xADDR` is 3.24.3 asm. Tag keys are halved Smi immediates, per the Smi rule in [../METHODOLOGY.md](../METHODOLOGY.md#smi-rule-reading-numbers-from-blutter-output); store offsets are Blutter byte offsets (not Smi-affected). Names are upstream's (`api/mqttmap.py`); a name of ours is marked `(no upstream name)`. Opcode `0079` (`setMomenryPortSwitch`) is also bound in the A1771 controller (audit row 240); its payload is documented on [a172x.md](a172x.md).

## Commands

### 0405 status message (param_info)

#### Purpose
Periodic status of a SOLIX F1200 (A1771): AC, DC, USB and PV power, battery and expansion state, firmware parts and the device settings.

#### Upstream name
No `A1771` key exists in `SOLIXMQTTMAP`; `mqtt_pps.py` lists `"A1771"` among the supported PPS models (line 34) and `apitypes.py` names it F1200 (lines 697 and 1196). The names below come from the sibling map `_A1761_0405` (C1000, `mqttmap.py` lines 322-381, bound at line 4269); for tags absent there the F2000 map `_A1780_0405` (lines 890-951, bound at line 4604) is shown as a hint only and is not applied. The old doc called A1771 "C1000" and quoted names as upstream-confirmed; `A1761` is the C1000 upstream (`apitypes.py` line 692). Tag: upstream-confirmed for the sibling-map names only.

#### Command code
`"0405"`, parsed by `A1771DeviceCommands.parseDeviceAllInfo` @0x4855438 (size 0x106c) and `parseWorkInfo` @0x485bb74 (size 0x1bb0) in `charging/ble/device/A1771/a1771_device_commands.dart`; the same file holds `_parseMemoryPort` @0x48564a4 and `parseSwitchStateInfo` @0x48579b0 (function start and size from the asm header). The message id is not bound by an audit row (upstream has no A1771 key). Asm-traced for the parsers.

New read 2026-10-20 (message id and topic, app side). `A1771DeviceController.handleMQTTDeviceResponse` @0x3b46ab0 calls `_dealWithMqttResponse` @0x3b46b18, which decodes the JSON body, tests `MqttServe.isDeviceParamInfoTopic` (@0x3b46cb4, so only the `param_info` topic of [iot.md](iot.md#mqtt-receive-path-and-topic-gate) passes), reads `payload` and `data`, base64-decodes `data` (@0x3b46e38) and calls `handleResponse` @0x3b46f54 (size 0xfc4). `handleResponse` runs `PPSDeviceCommands.parseResponse` (@0x3b47164) and then compares the `ZXOpcodeType` with pool constants: `getAllDeviceInfoRes` (index 0x25, @0x3b47654) and `postDeviceAllInfoReq` (index 0x52, @0x3b47664) lead to the status handling, `postCountDownTimeReq` (0x21) and `getAcCarCountDownTimeRes` (0x27) to `parseCountDownTime`, `postErrorInfoReq` (0x1d) to `parseErrorInfo`, `postWorkInfoReq` (0x1e), `postSwitchStateReq` (0x1f), `postDeviceInfoReq` (0x20, `praseDevieMessage`) and `postUpgradeStateReq` (0x65, `parseOTAUpdateProgress`). In the opcode map of [iot.md](iot.md#frame-decode-and-opcode-dispatch) the key `0405` is `postDeviceAllInfoReq`, so the A1771 status frame is the message id `0405`, as the heading says; the `0405` is the app's key, not a wire capture.

The tag set of this table splits between the two parsers: `parseDeviceAllInfo` @0x4855438 reads `fe`, `e3`, `d0` to `e4` and `_parseMemoryPort`; `parseWorkInfo` @0x485bb74 reads `f8`, `a2` to `cf` (all the other rows).

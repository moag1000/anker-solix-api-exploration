# A5101, A5102, A5103, A5341 (X1 HES power module) BLE

The X1 HES power module (A5101) and the codes that the factory builds with the same class (A5102, A5103, A5341). This page owns the BLE-specific facts of the product; the command payloads (opcodes, TLV tags, scales) are owned by the MQTT page [../mqtt/a5101.md](../mqtt/a5101.md) and are not repeated here. The frame, fragmentation and encryption are on [protocol.md](protocol.md), the negotiation on [handshake.md](handshake.md).

Evidence is the asm of 3.24.3 (`file.dart @0xADDR`, relative to `charging/ble/device/` unless a path is given). Pool lists such as `[0, 0x5e]` are real values. A row that says `no` in the column `on the MQTT page` means the opcode is not mentioned on the linked page; it can still be a command that also goes over MQTT.

Notes on this product:

- `A5101AnkerDevice` mixes in `ZXBleFeature` and `PpsDeviceFeature`; the factory builds it for `A5101`, `A5102`, `A5103` and `A5341` in one branch (`device_factory_impl.dart @0x240e8bc`). It uses its own GATT family (see [protocol.md](protocol.md#gatt-profile-per-product)) for A5101, A5102 and A5103; A5341 has the placeholder row. `a5101_anker_device.dart` calls `BleInfoHelper.clearAllAesKey` (`@0x37267a4`), which no other device class does.
- This product does not use the single opcode set of the other classes: three opcode classes decide the family. `ZXOpcodeBase` (`opcode/zx_opcode_0x01.dart`) holds handshake-style codes, `ZXPdpCode` (`zx_opcode_0x0f.dart`) and `ZXHesOpcode` (`zx_opcode_0x12.dart`) further opcode ranges, and `OpcodeTypeExtension` (`zx_opcode_base.dart`) has `isEncrypted`, `getOpcode`, `getOpcodeType` and `getFunctionType` over them. See the last command section below.
- The opcode `002d` is in `getBluetoothOTAStatus` (`a5101_device_controller.dart @0x42e8ae0`, size 0x1b4; the pool list is at `@0x42e8bc0` and the function logs `startBleOTA=========getBluetoothOTAStatus`), while `sendAutoDisasterDataCmd` (`@0x3ebdad8`, size 0x220) loads `0115` (`@0x3ebdc8c`). The MQTT page [../mqtt/a5101.md](../mqtt/a5101.md) and audit row 316 name `sendAutoDisasterDataCmd` for `002d`; the address `@0x42e8bc0` they cite lies inside `getBluetoothOTAStatus`, so that attribution is wrong.
- Negotiation, app side: `A5101AnkerDevice` (class id 8451) has `ZXBleFeature` in its `extends` line and `A5101`, `A5102`, `A5103` and `A5341` are not registered SDK product codes, so `BleHandler` picks `BleHandlerImpl1`, whose `_authDevice` starts the Dart `ZXBleConfer`. For these four codes `_authDevice` passes `needBind = false` (`ble_handler_impl_1.dart @0x4196d80`, from `_isA5101Pn` `@0x28574d4`), every other product `true`. Which of the three conferers then runs depends on the capability response, not on the product ([handshake.md](handshake.md#which-implementation-runs-for-a-product)).

#### Direction

both: requests go app to device, the responses (`08xx` in the common map, [handshake.md](handshake.md#opcode-pairs)) come back device to app.

#### Packet framing

[protocol.md](protocol.md#frame-on-ble); the handshake frames carry the flag bits of [protocol.md](protocol.md#opcode-byte-0-flags).

#### Handshake prerequisite

The rows of group `handshake` are the handshake. Which conferer runs (`SecureEcdhConfer`, `EcdhConfer` or `AesConferV1`) is chosen from the capability response, not from the product: [handshake.md](handshake.md#capability-negotiation-response). The other rows are ordinary commands that need a completed handshake for encrypted frames.

#### TLV tags

The handshake payloads are positional bytes or single tags and are not per-product; they are described in [handshake.md](handshake.md#capability-negotiation-response) and [handshake.md](handshake.md#the-three-conferers). The payloads of the WiFi, OTA and status-request rows were not decoded for this page.

#### Example

none: no capture of a handshake exists in this repository.

MQTT twin and device page: [../mqtt/a5101.md](../mqtt/a5101.md), [../devices/x1_hes_e10.md](../devices/x1_hes_e10.md). The handshake itself has no MQTT twin.

### Opcode families (zx_opcode_0x01, 0x0f, 0x12)

#### Purpose

The three opcode classes that make the A5101 a different protocol from the single opcode set of the other classes.

#### Upstream name

none; the MQTT page names the data-code enum (`A5101DataCodeType`) and upstream's `_X1_JSON`.

`OpcodeTypeExtension` (`opcode/zx_opcode_base.dart`: `isEncrypted` @0x23c5594, `getOpcode` @0x23c55f8, `getOpcodeType` @0x23c5650, `getFunctionType` @0x23c5850 region) reads the three maps. The `0x01` class holds the handshake pairs `0001`/`0801`, `0002`/`0802`, `0003`/`0803`, `0005`/`0805`, `0022`/`0822`, `0023`/`0823`, `0027`/`0827` and `0029`/`0829` of `commonOpcodeMap` and the request `0004`; the public-key pair `0021`/`0821` of the common map is not in this class, although `a5101_anker_device.dart` has a `getPublicKey` method with `0021` (see the table in the first command section). The `0x0f` and `0x12` classes hold further opcode ranges (`0022` to `0030` and `0100` to `0925`); what each range means was not decoded.

Consumers. `OpcodeTypeExtension.getOpcodeType` and `isEncrypted` are called only from two functions of the same name, `_getBleResponsePayload`: `A5101DeviceController._getBleResponsePayload` (`a5101_device_controller.dart @0x3b902a4`; calls `@0x3b903fc` and `@0x3b90424`) and its copy in `ui/page/device/a5101/ota/a5101_mqtt_logic.dart` (function `@0x23c53e4`; calls `@0x23c553c` and `@0x23c5564`). Each stores the opcode type and the encrypted flag of a received BLE response into two fields of its own object. `ZXBleConfer`, the three conferers and `PPSDeviceCommands.parseResponse` do not reference the three classes, so the negotiation of [handshake.md](handshake.md#opcode-pairs) reads `commonOpcodeMap` and not these maps.

Relation to `A5101Commands`. `setDataCodeMap` (`a5101_commands.dart @0x3b88c14`) has 98 literal entries with 92 distinct keys and `getDataCodeMap` (`@0x3b8aa84`) 91 entries with 85 distinct keys; each key is `bytesToHexString` of a two-byte list, like the keys of the three classes (17, 29 and 33 entries). The key ranges are mostly different (for example `f008`, `020f`, `0136` against `0022` to `0030` and `0100` to `0925`). Equal key values: 6 distinct set keys (`0001` to `0005` and `0023`) occur in `ZXOpcodeBase` and 2 (`0023`, `0028`) in `ZXPdpCode`; 5 distinct get keys (`0001` to `0005`) occur in `ZXOpcodeBase`; none occur in `ZXHesOpcode`. No function reads both an opcode class and a data-code map (the two files do not reference each other), so no mapping between them exists in the asm; whether equal key values denote the same operation is not decoded.

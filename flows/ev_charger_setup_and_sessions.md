# EV charger lifecycle: setup, RFID cards, vehicles, charging orders, OCPP (A5190 / A5191)

What the app does around an EV charger beyond starting a session: the first-time setup pages after binding, RFID cards, vehicles, charging orders and history, and the OCPP server setting. Starting, stopping and boosting a session is [ev_charger_start_charging.md](ev_charger_start_charging.md); Modbus on the charger's "Integrations" page is [../devices/modbus.md](../devices/modbus.md#ev-charger-modbus-tcp-device-properties). The device facts (property names, value tables) are owned by [../devices/ev_charger.md](../devices/ev_charger.md); the kit identifiers by [../reference/iot_kit_channels.md](../reference/iot_kit_channels.md); the response classes by [../models/ev_charger_device_models.md](../models/ev_charger_device_models.md), [../models/ev_charger_vehicle_models.md](../models/ev_charger_vehicle_models.md) and [../models/ev_charger_session_models.md](../models/ev_charger_session_models.md). This page links to the owners and copies no payload. Upstream names (`api/apitypes.py` of the upstream library) are used where they exist.

Scope: app side only. Which transport the IoT kit uses for a property read or write, and what the server does with a cloud call, are not facts of this page. Every `akiot.cloud_api` call of the charger module (the kit carries it as an HTTP request, owner pages: the endpoint pages linked below) is sent from `AKIotEVChargeCommand` in `ev_charger/src/ev_charger/sdk/command/ev_charge_command.dart`.

## Preconditions

- A bound A5190 or A5191 charger in the account; the cloud calls need a login. Which accounts the server accepts (owner, member, shared) is server behaviour; upstream notes "needs owner" for `get_device_rfid_cards` and "works as member" for the order statistics (`api/apitypes.py` lines 195, 148, 149, upstream-confirmed as notes, not as app facts).
- Reads and writes of device properties (`prop_read_*`, `prop_write_*`) go through the IoT kit; the app shows the BLE connect sheet or a retry only on the paths named in the steps. The BLE and WiFi exclusion is described on [../ble/protocol.md](../ble/protocol.md) and is not repeated here.
- The OCPP page is reached only through the firmware gate of step E1.

## Side effects

- B: an add or delete changes the card on the charger first and the cloud list second; the cards page gets the new alias or the removal through an event bus message (steps B9, B10), not by reloading.
- A: the charger gets `initSettings` = 1 and the maximum current in one write (step A10); that is the only setup state the app writes in the sub-flow.
- C: app side, the pickers call the list endpoint when they open, so a new vehicle appears in them only through that call (no local copy was found).
- D: a deleted order disappears from the list through `needRefresh`; the statistics are not reloaded by the delete itself (not decoded whether the list page reloads them).
- E: app side, the app treats a saved OCPP server as replacing the previous one (one `prop_write_ocpp_info` write of the whole record); the app shows the disconnect warning first (step E5) because of this.
- Analytics events are written at most steps (`ev_event_duration`, `ev_is_success`, `ev_failure_reason` and similar keys); none of them is a request to the cloud.
- Link between steps A1 and A2 (traced): `IotAnkerDeviceConfigBuilder.build` (`base_service/util/iot_device_config.dart @0x45448dc` to `@0x4544aac`) loads the builder field at offset 0x37 (the one `withDeviceBindInitPage` fills with `/chargerAccessInitialPage`, `@0x45ab00c` to `@0x45ab018`) and stores it into the built configuration at offset 0x1b (`@0x4544a70`, `@0x4544a74`); `getDeviceBindAfterPage` reads offset 0x1b of the configuration found by product code (`@0x35099d4`). So the registered string is the page A2 navigates to.

## Timing (delays/polling)

- 1 s after a successful setup write (step A11, pool `Duration` `pp+0x1458`, 1,000,000 microseconds).
- No polling in B, C, D; E4 follows the kit event stream (no timer of its own was found).
- The size of a page of the order list and the date ranges are owned by the endpoint pages; the app side only pages with the pull-to-refresh controller.

## Failure paths

- Property write or read fails (A7, A8, A10, B5 to B7, E3, E7): toast or dialog as named in the step; no retry in Dart except the retry dialog of step A6. Error codes of the cloud calls: [../api/errors.md](../api/errors.md).
- The cloud list call fails (B3, C1, D3 to D5): `failedToLoad` or `commonNetWorkErrorFix` on the pages that show it; the card list and the vehicle list only log.
- RFID: a write succeeded but `save_device_card` fails: the app has sent the card to the charger and has not stored it in the cloud call (step B8 sends the cloud call after the write); whether the charger kept it is not visible; the toast is `addFailure`. The reverse holds for delete (step B10).
- Charging while editing OCPP (E5, E7): the app refuses with `showChargingDialog`, nothing is written.
- Deleting a vehicle in use shows `evVehicleDeleteIsCharging` (step C7).

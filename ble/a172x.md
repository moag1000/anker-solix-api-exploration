# A1722, A1723, A1725, A1726, A1727, A1728, A1729 (SOLIX C200 and C300 family) BLE

The SOLIX C200/C300 portable power stations. Seven product codes share one device class. This page owns the BLE-specific facts of the product; the command payloads (opcodes, TLV tags, scales) are owned by the MQTT page [../mqtt/a172x.md](../mqtt/a172x.md) and are not repeated here. The frame, fragmentation and encryption are on [protocol.md](protocol.md), the negotiation on [handshake.md](handshake.md).

Evidence is the asm of 3.24.3 (`file.dart @0xADDR`, relative to `charging/ble/device/` unless a path is given). Pool lists such as `[0, 0x5e]` are real values. A row that says `no` in the column `on the MQTT page` means the opcode is not mentioned on the linked page; it can still be a command that also goes over MQTT.

Notes on this product:

- One base class `A172xAnkerDevice` carries the behaviour; each code has an empty subclass file (`1722AnkerDevice.dart` and the others), and `A1728AnkerDevice` extends `A1726AnkerDevice`. `DeviceFactoryImpl.createByProductCode` builds the code's own subclass (for example `A1722AnkerDevice`, `device_factory_impl.dart @0x240ec90`) and gives all seven the same `A172xDeviceController` (`@0x240eca0` for A1722).
- `A1726DeviceCommands` (`a1726_device_commands.dart`) is a separate parser class next to `A172xDeviceCommands`; the audit's A1726 tag counts come from it (audit rows 440 to 458).
- The updateStatus function of `AnkerDevice` does not test the A172X codes (see the table in [protocol.md](protocol.md#connection-routing-and-the-wifi-exclusion-rule)); the status logic for them is outside that function.

#### Direction

both: requests go app to device, the responses (`08xx` in the common map, [handshake.md](handshake.md#opcode-pairs)) come back device to app.

#### Packet framing

[protocol.md](protocol.md#frame-on-ble); the handshake frames carry the flag bits of [protocol.md](protocol.md#opcode-byte-0-flags).

#### Handshake prerequisite

The rows of group `handshake` are the handshake. Which conferer runs (`SecureEcdhConfer`, `EcdhConfer` or `AesConferV1`) is chosen from the capability response, not from the product: [handshake.md](handshake.md#capability-negotiation-response). The other rows are ordinary commands that need a completed handshake for encrypted frames.

#### TLV tags

The handshake payloads are positional bytes or single tags and are not per-product; they are described in [handshake.md](handshake.md#capability-negotiation-response) and [handshake.md](handshake.md#the-three-conferers). The payloads of the WiFi, OTA and status-request rows were not decoded for this page.

#### Example

none: no capture of a handshake exists in this repository.

#### Related API endpoint

MQTT twin and device page: [../mqtt/a172x.md](../mqtt/a172x.md). The handshake itself has no MQTT twin.

# A1340 MQTT commands (portable power bank)

Portable power bank A1340: the per-port parser and the device-level debug labels. The envelope, topics, frame layout and data type codes are owned by [envelope.md](envelope.md).

Evidence rows are written `audit row N` and refer to [../docs/audit/BLE_COMMAND_MAP.md](../docs/audit/BLE_COMMAND_MAP.md); `file.dart @0xADDR` is 3.24.3 asm. Tag keys are halved Smi immediates (per the Smi rule in [../METHODOLOGY.md](../METHODOLOGY.md#smi-rule-reading-numbers-from-blutter-output)). The header tag is `string-only` because the device-level labels are debug strings. ## Commands

### parseUploadChargePortInfo (per-port tags)

#### Purpose
Reads the per-port values (status, voltage, current, power, repeat) that a portable power bank A1340 uploads for its charge ports.

#### Upstream name
none: upstream has no `A1340` entry (`mqttmap.py`, `apitypes.py`).

#### Command code
No command code. `A1340DeviceCommands.parseUploadChargePortInfo` @0x3b92108 (size 0x518; `charging/ble/device/A1340/a1340_device_commands.dart`); the same file has `parseAllChargePortInfo` @0x3b929d0, `parseChargePortInfo` @0x3b92df4, `parseDeviceAllInfo` @0x3b96028 (size 0x1004) and `parsePortDataCurveInfo` @0x33e705c (function start and size from the asm header). Asm-traced for the tag set; the labels are string-only.

#### Direction
device→app. Tag: asm-traced.

#### Topic pattern
Not applicable: the audit does not bind the parser to an MQTT topic.

#### Payload fields
The old doc listed five fields for four ports (USB-C1, USB-C2, USB-A, DC/P). The audit confirms that `parseUploadChargePortInfo` reads the tags a2 to aa, with a6 read twice (audit row 351). New read 2026-10-20: the tags a2, a3, a4 and a5 are the four port blocks. Each is fetched as a `List<int>` (`indexString` arguments 162 to 165 @0x3b92174, @0x3b921c0, @0x3b9220c, @0x3b92258), the four lists go into one growable list (`AllocateArray` with r2 = 8, a tagged length, so 4 elements, @0x3b922a8) that is passed to `parseAllChargePortInfo` @0x3b929d0 (call @0x3b922f8). That function requires exactly 4 entries (`cmp x1,#4` after `LoadInt32Instr` @0x3b92a20, 64-bit, real value) and hands entry 0, 1, 2, 3 to `parseChargePortInfo` @0x3b92df4, storing the results at object offsets 447, 451, 455 and 459 (32-bit stores into tagged slots, raw offsets) under the log labels `c1端口信息: `, `c2端口信息: `, `a端口信息: ` and `p端口信息: ` (@0x3b92aac, @0x3b92b90, @0x3b92c74, @0x3b92d58). So the tag order a2, a3, a4, a5 is the port order C1, C2, A, P (app side). `parseDeviceAllInfo` @0x3b96028 uses the same shape on the tags a4 to a7 (call at the a7 read, @0x3b96270). The old doc scales (voltage "x0.1 V?", current "x0.01 A?") are UNVERIFIABLE (audit row 650): the file contains `double(0.01)` constants but the binding to the voltage and current fields is not read.

#### Transport and message ids
App side, new read 2026-10-20. `a1340_device_controller.dart` defines `handleZXProtocolDeviceResponse` @0x3b90574 (size 0x7f0) and no `handleMQTTDeviceResponse`; the base `device_controller.dart` has none either (its function list holds `_initMQTTDeviceResponse` @0x242e12c, which listens to a stream and calls a virtual hook through a dispatch table, so the name is not visible). In this file the parsers are therefore reached from the ZX protocol handler, which is the BLE entry of the other controllers ([iot.md](iot.md#fallback-handler-iotdevicecontroller)); an MQTT entry for A1340 is not present in these two files. Inside the handler the opcode key is compared with `listEquals` against pool lists: `[0xd, 0]` @0x3b90748 (log `getDeviceAllInfoRes`) calls `parseDeviceAllInfo` @0x3b90788; `[0x5, 0xe]` @0x3b90954 (log `uploadChargePortInfoReq`) calls `parseUploadChargePortInfo` @0x3b90990; `[0x5, 0xf]` @0x3b909b4 (`uploadChargeStateInfoReq`) calls `parseUploadChargeStateInfo`; `[0x5, 0x17]` @0x3b90a80 calls `paresBuzzerTimeInfo`; `[0x5, 0x13]` @0x3b90ad0 (`uploadOptimizeSwitchStateReq`) calls `parseuploadOptimizeSwitchState`; `[0x5, 0x19]` @0x3b90b30 calls `parseCurrentOptimizedStateInfo`; `[0x5, 0x22]` @0x3b90c00 calls `parseCurrentBatteryTemperatureState`; `[0x5, 0x25]` @0x3b90cc0 calls `parseUploadPortSettingInfo`. The pool lists are the two opcode bytes (the first byte after the `& 0xf` mask of [iot.md](iot.md#frame-decode-and-opcode-dispatch)), real values.

#### parseChargePortInfo block shapes
`parseChargePortInfo` @0x3b92df4 (size from the asm header) rejects an empty block (log `接口信息为空`) and a block shorter than 7 bytes (`cmp x1,#7` after `LoadInt32Instr`, 64-bit, real). It then switches on the block length with Smi compares: `cmp w0,#0xe` @0x3b92f8c (7 bytes) builds `ChargePortInfo` with the named argument `maxChargePower` (call @0x3b93000); `cmp w0,#0x12` @0x3b93034 (9 bytes) builds it with no named argument (call @0x3b93070); `cmp w0,#0x16` @0x3b930e4 (11 bytes) builds it with the named arguments `chargeProtocol`, `protocolCurrent` and `protocolVoltage` (descriptor `[0, 0x7, 0x3, 0x4, chargeProtocol, 0x4, protocolCurrent, 0x6, protocolVoltage, 0x5, null]` @0x3b93218, call @0x3b93220); any other length logs `接口信息长度不对`. So the per-port field `chargeProtocol` of the old doc exists in the 3.24.3 app and is set only from an 11-byte block. The widths of the sublist ranges are not decoded here.

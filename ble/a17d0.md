# A17D0 (Generator Input Adapter) BLE

The app has no BLE profile, no device class and no controller for A17D0 in 3.24.3. The app handles it only as an accessory entry (a sub-package record) that hangs off an A1790, A1790P or A17B1 device. This page owns that negative result and the three places where the app reads or builds the record; the MQTT keys of the two A17B1 slots are owned by [../mqtt/a17b1.md](../mqtt/a17b1.md), the host products by [a1790.md](a1790.md) and [a17b1.md](a17b1.md). The frame, fragmentation and encryption are on [protocol.md](protocol.md), the negotiation on [handshake.md](handshake.md).

Evidence is the asm of 3.24.3 (`file.dart @0xADDR`, relative to `charging/` unless a path is given). A number printed as a byte offset is a raw object offset, not a Smi.

## Commands

### A17D0 sub-package record (no opcode of its own)

#### Purpose

Describes how the app turns an A17D0 attached to an A1790, A1790P or A17B1 into a `SubPackageModel` entry; it sends no command to the adapter.

#### Upstream name

none (no upstream name for the record; the A17B1 slot keys are `device_1_*` and `device_2_*` on [../mqtt/a17b1.md](../mqtt/a17b1.md)).

#### Opcode

Tag: asm-traced.

None found: no controller class and no opcode list exists for this product (negative result of a grep over the asm tree for the literal, see [BLE profile](#ble-profile)), so no `ZXOpcodeType` value belongs to it. The only A17D0 facts are the record sites in the table under Direction.

#### Direction

device to app (the record is built while a status message of the host is parsed).

Tag: asm-traced.

| site | what the function does | citation |
|---|---|---|
| `A1790DeviceCommands._updateA17D0SubPackageModel` | builds the string key `<productCode>_<string field>`, removes an existing entry with that key (`firstWhereOrNull` and `remove`), then, if one numeric field of the host is non-zero and three further fields are non-null, builds `SubPackageModel(batteryId, sn)` whose name comes from `SpUtil.getAccessory("A17D0")`, and appends it to the host's sub-package list | a1790_device_commands.dart @0x3b453e8, `getAccessory` call @0x3b455ac |
| callers of that function | `_updateSubBatteryList` and `parseThirdATSInfo` | call sites @0x3b43c90 and @0x4854a94 in a1790_device_commands.dart |
| `A17B1DeviceCommands.parseDeviceAllInfo` slot a | tests a string field of the parsed object (raw byte offset 1223) against `"A17D0"`; the A17D0 arm reads four map keys (`90as`, `90asoc`, `90asn`, `90av`), the other arm reads five (the same four and `90aacc`) | a17b1_device_commands.dart @0x3b4cdd0, keys @0x3b4cdf4 to @0x3b4cfa0, other arm @0x3b4d04c to @0x3b4d2dc |
| `A17B1DeviceCommands.parseDeviceAllInfo` slot b | the same test on the string field at raw byte offset 1227; A17D0 arm keys `90bs`, `90bsoc`, `90bsn`, `90bv`, other arm adds `90bacc` | a17b1_device_commands.dart @0x3b4d374, keys @0x3b4d398 to @0x3b4d538, other arm @0x3b4d5e4 to @0x3b4d864 |
| `A17B1DeviceCommands.parseDeviceAllInfo` end | clears the host's sub-package list (@0x3b4d8f4); if slot a or slot b holds `"A17D0"` builds `SubPackageModel(batteryId, sn)` with the name `"A17D0"` and appends it, otherwise resets three fields of the host | a17b1_device_commands.dart @0x3b4d910, @0x3b4d948, @0x3b4d9d0, reset @0x3b4d974 |
| `A17B1AnkerDevice.getSubPackageList` | returns the result of an `==` compare of one string field against `"A17D0"` | a17b1_anker_device.dart @0x26ed594 |

The map keys are the strings the parser looks up; their value types and the meaning of the `acc` keys were not decoded here.

#### Packet framing

[protocol.md](protocol.md#frame-on-ble); the record is built while the host's status message is parsed, not from a frame of its own (frame ids of the hosts: [a17b1.md](a17b1.md), [a1790.md](a1790.md)).

#### Handshake prerequisite

The host's handshake applies ([handshake.md](handshake.md)); the app builds no session for the adapter.

#### TLV tags

Owned by the MQTT page of the host: the keys `90as`, `90asoc`, `90asn`, `90av`, `90bs`, `90bsoc`, `90bsn` and `90bv` are rows of [../mqtt/a17b1.md](../mqtt/a17b1.md); `90aacc` and `90bacc` are not rows there.

#### Example

none: no capture of an A17D0 exists in this repository.

#### Related API endpoint

Host pages: [a1790.md](a1790.md), [a17b1.md](a17b1.md), [../mqtt/a1790.md](../mqtt/a1790.md), [../mqtt/a17b1.md](../mqtt/a17b1.md), [../devices/home_power_panel.md](../devices/home_power_panel.md). The cloud ships the adapter as a sub-package of those hosts; its product code has no API page.

#### Since/changed

3.18.0: the archive section above (A17B1 parser plus A1790). 3.24.3: the same two hosts, five sites in the A17B1 parser and the separate `_updateA17D0SubPackageModel` on the A1790 side.

#### Known unknowns

- The name and meaning of the A17B1 string fields at raw byte offsets 1223 and 1227 (slot product codes are the only reading the compares support).
- Value types behind the keys `90aacc` and `90bacc` and why the A17D0 arm omits them.
- Whether the adapter has a BLE profile of its own in the firmware; the app has none.
- Whether the A1790 side `<productCode>_<string field>` key is an A17D0 serial or a slot id.

BLE is unavailable while the device is on WiFi; see `ble/protocol.md` (community finding, see protocol.md; not asm-traced).

none.

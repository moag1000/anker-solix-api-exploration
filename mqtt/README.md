## Source conflicts (two-sided; app side re-checked 2026-10)

Each bullet carries a trailing `Re-checked 2026-10` clause with one verdict: `asm confirms side A`, `asm confirms side B` or `asm silent, device test row N`. Side A is the reading a bullet names first, side B the one it names second; the clause also names the reading. A verdict is about what the 3.24.3 app code does (app side), never about what a device does; the device side of every conflict stays a device test ([../docs/DEVICE_TEST_BACKLOG.md](../docs/DEVICE_TEST_BACKLOG.md)) and no upstream side is deleted.

- **007e timer bytes (A17X8):** the asm builds the 3-byte timer values with `intToList3(seconds)` (little-endian integer; [a17x8.md](a17x8.md), docs/audit/devices.md row 76, [devices/smart_plug.md](../devices/smart_plug.md)); upstream `mqttmap.py` `_PLUG_TIMER_STATUS` labels the same 3 bytes `seconds:minutes:hours` (type `var`). Both readings agree for values below 256 s; a device test with a timer above 4 min 15 s decides (backlog row on the A17X8 group). **Re-checked 2026-10:** asm confirms side A (app-side encoding only). `CmdUtil::intToList3` @0x2e65c28 (size 0x9c) returns `[x & 0xff, (x >> 8) & 0xff, (x >> 16) & 0xff]` (`and w3,w2,#0xff` @0x2e65c40, `asr x2,x1,#8` @0x2e65c44, `asr x2,x1,#0x10` @0x2e65c54; `AllocateArray` r2 = 6, i.e. 3 elements), so byte [0] is the least significant byte: little endian. `setCountdownCmd` @0x3dcfba4 calls it twice with one integer each (@0x3dcfbe4 with the first value, @0x3dcfc1c with `max(0, first - second)`), and the countdown setting page builds that integer as one sum, hours x 60 x 60 + minutes x 60 + seconds (unboxed 64-bit `mul x, x16 = 60` @0x3dd159c, @0x3dd15a4, @0x3dd15e4 in `a17x8countdown_setting_logic.dart`). The read side `parseCountDownInfo` uses the same little-endian `listToInt` (shift `lsl x4,x2,x3` with x3 = 8 x index, @0x23c42f4). The app never splits the time into three seconds, minutes and hours bytes; how the firmware reads the three bytes stays device test row 63 (readback: row 64).

- Tag `fd`: upstream describes a millisecond timestamp string, the app builders write a CRC32 (audit rows 24, 219-221). See [envelope.md](envelope.md#tlv-frame) and [a17c1.md](a17c1.md#005e-setbackpower-settacticstime-setpeakvalley). Untested here. **Re-checked 2026-10:** asm confirms side B (app builders write a CRC32; app side only). The `fd` key is raw 506 = 0x1fa stored as a tagged map key (Smi, so 253 = 0xfd) next to `Crc32` -> `ParametricCrc` (raw 4294967295 twice) -> `convert` -> `intToList4` in `A17C1DeviceController` @0x281aa44..0x281aa94, @0x288b238 and @0x428b0a8; no other file under `charging/ble` stores key 506. A millisecond string under `fd` (upstream's `CMD_COMMON_V2` format for newer devices) is not written by any app builder, and whether a device accepts it stays device test row 30.
- A17C1 tag `e0`: the parser tests `== 7` (audit row 395), upstream lists 1, 6 and 3. See [a17c1_status.md](a17c1_status.md#payload-fields). **Re-checked 2026-10:** asm confirms side A (app side only). In `A17C1DeviceCommands.parseDeviceAllInfo` the `e0` block (`indexString` argument 224 = 0xe0 @0x48662c0, call @0x48662c4) calls `listToInt` @0x4866310, which returns its accumulator unboxed (`ret` with the raw sum in x0, loop @0x23c4240), then `cmp x0,#7` @0x4866314 against raw 7 and stores the result as a bool; no compare against 1, 3 or 6 occurs in that block. What value a device sends in each grid state stays device test row 35.
- Opcode `005a`: the app has no builder (audit row 222) while [../devices/solarbank.md](../devices/solarbank.md) lists it as tested. See [a17c1.md](a17c1.md#opcodes-without-a-confirmed-app-builder-005a-0082-006a-0069). **Re-checked 2026-10:** asm confirms side A (app side only). Opcodes are built from pool lists of the two opcode bytes (for example `r2 = const [0, 0x5e]` @0x281aadc in `setBackPower`); `pp.txt` holds no `[0, 0x5a]` list (`grep -c` gives 0, against 1 for `[0, 0x5e]`), no asm file uses one, and neither opcode map of [iot.md](iot.md#frame-decode-and-opcode-dispatch) has a `005a` key. Whether a device accepts `005a` is the mqtt_monitor claim of solarbank.md and stays device test row 37.
- A2345 message id: the old doc calls the parser "0405", upstream binds `"0a00"` and `"0303"` for A2345 and A91B2 and has no `"0405"` for either; the 2026-10 re-read binds both parsers to `0a00` and the port branch to `0303` (app side; the earlier audit left it unbound) (the old doc mentions A91B2 only as a 4th port). See [a2345.md](a2345.md#parsedeviceallinfo-status-tags-upstream-message-0a00) and [a91b2.md](a91b2.md#parsedeviceallinfo-status-tags-upstream-message-0a00). **Re-checked 2026-10:** asm confirms side B (upstream `0a00` and `0303`; app side only). In the A2345 controller `OPCODE_KEY == [0xa, 0]` (`listEquals` @0x3b28b18, log `getAllDeviceInfoRes` @0x3b28b24) leads to `parseDeviceAllInfo` @0x3b28c04 and `OPCODE_KEY == [0x3, 0x3]` (@0x3b28fe0) to `parseUploadDCPortState` @0x3b2902c; the controller has no `[0x4, 0x5]` compare. The A91B2 controller does the same (`[0xa, 0]` @0x3b5d300 to `parseDeviceAllInfo` @0x3b5d3e4, `[0x3, 0x3]` @0x3b5d63c to its `uploadDCPortState` branch). `OPCODE_KEY` is the opcode bytes with element 0 masked by `& 0xf` ([iot.md](iot.md#frame-decode-and-opcode-dispatch)), so the app binds the ids 0a00 and 0303 and not 0405. The ids on the wire stay device test row 94 (A2345) and row 96 (A91B2).
- A2345 port tags: upstream has six port blocks (`a4` to `a9`), the old doc listed `a4` to `a6` as port blocks and `a7` to `ab` as plain ints; the asm calls the port sub-parser six times. Same pages. **Re-checked 2026-10:** asm confirms side A (upstream: six port blocks `a4` to `a9`; app side only). In `A2345DeviceCommands.parseDeviceAllInfo` the six `parseChargePortInfo` calls (@0x3b3024c, @0x3b302b8, @0x3b30324, @0x3b30390, @0x3b303fc, @0x3b30468) take the payload entries of `indexString` 164 to 169 (`a4` to `a9`; the key loads are `ldur x2,[fp,#-0x30]` .. `[fp,#-0x58]` @0x3b30218, @0x3b30284, @0x3b302f0, @0x3b3035c, @0x3b303c8, @0x3b30434, slots filled in read order from `a2` at [fp,#-0x20]), and the five `parseChargePortACInfo` calls take `aa` to `ae`. The old doc's `a7` to `ab` as plain ints does not match the code. Units per port stay device test row 95.
- `f8` port saving modes (A1753, A1790): upstream (A1761/A1780 maps) calls bytes [0] and [1] Normal (1) / Smart (2); the app enum maps 1 to close and 2 to open (audit rows 313, 515). See [a1753.md](a1753.md#payload-fields) and [a1790.md](a1790.md#known-unknowns). **Re-checked 2026-10:** asm confirms side B (app enum: 1 close, 2 open; app side only). A1753 `parseDeviceAllInfo` reads `f8` (`indexString` 248 @0x484f25c) as a byte list; for bytes [0] and [1] the compare is against tagged values, `cmp w0,#2` (Smi 2 = 1) selects [pp+0x551a0] `close` and `cmp w0,#4` (Smi 4 = 2) selects [pp+0x551a8] `open`, anything else [pp+0x15a60] `notSupport` (@0x484f320..0x484f348, stored at offsets 415 and 419). A1790 holds the same compares (@0x484fbdc, @0x484fbf0). Whether the device sends 1 and 2 as Normal and Smart stays device test row 80 (A1790) and row 93 (A1753 extra tags).
- A17C2 field labels: the debug strings in the parser (for example `ab` total output power) conflict with the upstream names via the A17C5 map (`ab` `photovoltaic_power`). See [a17c2.md](a17c2.md#payload-fields). **Re-checked 2026-10:** asm silent, device test row 44. The only app-side evidence for the meaning of these tags is the log label of each tag (`A17C2 总输出功率(W) ab:` @0x485e4b8, string-only); the stored values were not traced to a UI use or a field name, so the asm does not choose between the labels and the upstream names.
- A1771 names: upstream has no A1771 key; the sibling maps (A1761, A1780) disagree with the old doc labels at `a5`, `d1`, `d5` and at `a2`/`a3`. The A1771 parser holds no label for `a2`, `a3`, `a5`, `d1` or `d5` (its debug strings, for example @0x4856304, concern other fields) and upstream has no A1771 key.

In `A1780Commands.parseOtherData` window [66, 67) is read with `listToInt`, tested `cmp x0,#0x80` and `sub x1,x0,#0x100` (signed 8-bit) and stored at offset 787 (0x313), the 3.24.3 temperature offset of the family parsers (@0x45ecd40..0x45ecda8, audit row 58); window [61, 63) is stored at 767 (0x2ff) and passed to `getMainVersion` (@0x45ecbc4, @0x45ecc3c), so it is not a temperature.

# OTA monitor (re-attaching to a running firmware update)

How the `ota_kit` package finds out that a device is already updating (opened the OTA page late, returned to the app, or restarted it) and follows the update without starting it: it asks the AK IoT kit whether an OTA is in progress, subscribes to the progress stream, and starts polling only on stream timeout (step 7); a firmware version check decides the result when no update is running. The channels `akiot.device.is_ota_in_progress`, `akiot.device.monitor_ota` and `akiot.device.monitor_ota_progress` are new in 3.24.3 and are owned by [../reference/iot_kit_channels.md](../reference/iot_kit_channels.md); starting an update is a different call (`akiot.device.start_ota`, listed there). The old FLOWS.md has no OTA flow and no audit rows.

## Trigger (UI action)

- Single device: opening the single-device OTA page runs `SingleDeviceOtaController.onInit`, which calls `OTARemoteObserver.checkAndEnterOnPageEntry` (`single_device_ota_controller.dart @0x3631ef0`, function `ota_remote_observer.dart @0x3632e50`).
- Single device, return to the app: `onOTAResumeCheck` calls `OTAResumeCoordinator.handleResumeCheck` (`single_device_ota_controller.dart @0x4716b84`, function `ota_resume_coordinator.dart @0x2ecad7c`).
- Batch: `BatchDeviceOtaController._resumeColdStartOTA` and `_doResumeDecision` call `BatchOTAStrategy.reattachToRunningOTA` (`batch_device_ota_controller.dart @0x362e3b8`, `@0x4715dac`; function `batch_ota_strategy.dart @0x362e414`).

## Preconditions

- A non-empty device serial: `isDeviceOTAInProgress` returns false without an SDK call for an empty serial (`ota_remote_status_service.dart @0x2ecf1b8`, warning text at `@0x2ecf1d8`); `checkOTAInProgress` filters empty serials out of its list and skips the call when none is left (`@0x2ecf4b8`, `@0x2ecf54c`).
- The page has a state the observer may use: the observer mode flag must be set before a progress frame is accepted (see step 5).
- Stale flags: a device flag `isOTA` that is true while the local task is already in a terminal state is treated as a leftover of the restart window and not as a running update (`ota_device_truth.dart @0x2ed4250`; terminal states `completed`, `failed`, `cancelled`, `ota_device_truth.dart @0x2ed42ec`, `@0x2ed42fc`, `@0x2ed4314`). A device whose firmware already equals the target is treated as done and the observer is not entered (`@0x2ed4130`).

## Side effects

- Event bus messages `OTAProgressEvent` and `OTACompleteEvent` update the OTA pages (`ota_remote_observer.dart @0x2ecbed8`, `@0x2ecc14c`).
- Entering observer mode recreates the Wi-Fi progress tracker and sets the status to `upgrade`; leaving it through `exit` or `cleanup` sets a terminal status.
- Reconnection on resume: `_ensureConnectionForResume` waits for the device to come online, then rechecks once after a delay (see Timing).
- Event payloads (app side, `ota_kit/src/events/ota_events.dart`): `OTAProgressEvent` carries `deviceSn`, `progress` (printed with a percent sign by its `toString`) and `phase`; `OTACompleteEvent` carries a result and, on failure, the reason text (the `reason` of step 6; the class has no `toString` and its fields were not listed). Batch progress is an unweighted mean: `BatchProgressAggregator.calculateOverallProgress` (`batch_progress_aggregator.dart @0x362980c`) sums the per-device progress values as doubles (`fadd`, `@0x36298ec`), divides by the number of devices minus the removed ones (`fdiv`, `@0x3629920`) and rounds (`LibcRound`). The weighted progress of one device uses `OTAWeightConfig` (`ota_weight_config.dart`): a `SinglePackageWeights` with three integer fields and a `MultiPackageWeights` with five, chosen per device type by `OTAWeightRegistry.getConfigOrDefault` (`ota_weight_registry.dart @0x49837f0`, falls back to a default instance); which phase each weight belongs to was not read.

## Timing (delays/polling)

- Monitor subscription timeout: the pool `Duration` `pp+0x1bca8` with `off_8` 0x23c34600 = 600,000,000 microseconds, 10 minutes, used when `getTimeout()` is null (`ota_remote_observer.dart @0x2ecb79c`); the observer converts the `Duration` to a number with a division by 1,000,000 (`@0x2ecb7b0`) before it calls `monitorOTAProgress`; the unit that the kit expects for `timeOut` was not read.
- Result polling every 60 s: pool `Duration` `pp+0x1d8e0` with `off_8` 0x3938700 = 60,000,000 microseconds (`@0x2ecee94`). Two zero-progress polls end the observation (`cmp x1, #2` at `@0x2ecf034`; the Smi raw 4 in the log text at `@0x2ecf008` is 2).
- Resume: waiting for the device to come online polls every 500 ms (pool `Duration` `off_8` 0x7a120) for at most 20 s (`off_8` 0x1312d00) (`ota_resume_coordinator.dart @0x2ed4a68`, `@0x2ed4aec`); if the connection is still missing it rechecks after 15 s (`off_8` 0xe4e1c0 = 15,000,000 microseconds, `@0x2ed488c`). All are pool object values, not register immediates.
- A progress frame with a value of 100 or more also makes the observer read `isAllTasksComplete` (`cmp x0, #0x64` at `ota_remote_observer.dart @0x2ecbe30`, unboxed 100).
- Batch re-attach `timeOut`: the map built in `reattachToRunningOTA` holds `timeOut` as the Smi stored with `stur w16` of the raw 1200000 (`batch_ota_strategy.dart @0x362e72c`, `@0x362e734`), so 600000, next to `snList` and the identifier `akiot.device.monitor_ota` (`@0x362e74c`). The single-device observer passes the default 10 minutes as 600,000,000 µs divided by 1,000,000 (`sdiv` at `ota_remote_observer.dart @0x2ecb7c0`), so 600. The two values differ by a factor of 1000; which unit the kit expects is not visible in Dart.

## Failure paths

- `is_ota_in_progress` fails: the log text `查询失败` and the fallback to the device attribute `isOTA` (`ota_remote_status_service.dart @0x2ecf624`, `@0x2ecf2e4`); an exception logs `查询异常` (`@0x2ecfe28`).
- Observer stall: after two polls without progress the update is settled as failed (step 8).
- Monitor subscription error: `onError` of the listener; the text `启动远程进度订阅失败` is logged when the subscription cannot start (`ota_remote_observer.dart @0x2ecb884`).
- A terminal frame that is not `success` fires `OTACompleteEvent` with the reason. Error codes: [errors](../api/errors.md).

## Since/changed

All three channels, the observer, the device-truth rules and the resume coordinator are new in 3.24.3 (the three identifiers are marked new in [../reference/iot_kit_channels.md](../reference/iot_kit_channels.md#changed-since-3180)). The old FLOWS.md did not cover firmware updates.

## Known unknowns

- Which transport the kit uses for `is_ota_in_progress` and the progress stream: the resume coordinator labels its remote check "MQTT-reliable" (log text `ota_resume_coordinator.dart @0x2ecb054`), but the kit's choice is not visible in Dart. The app has a notion of a BLE OTA (`akiot.device.send_ble_ota_progress`, the parallel OTA page of the A1780P), but nothing here shows BLE as a live fallback while the device is on WiFi (see [../ble/protocol.md](../ble/protocol.md#connection-routing-and-the-wifi-exclusion-rule)) — reclassified 2026-10-20: native plugin, not in Dart asm, [device test row 128](../docs/DEVICE_TEST_BACKLOG.md#flow-device-and-model-findings-that-need-a-device-asm-depth-pass-task-5d).
- The unit of the `timeOut` argument for the kit: the app passes 600 for the single-device observer (the default 10 minutes divided by 1,000,000 as a microsecond count) and 600000 for the batch re-attach (see Timing); the unit is decided inside the native plugin — reclassified 2026-10-20: native plugin, not in Dart asm, [device test row 128](../docs/DEVICE_TEST_BACKLOG.md#flow-device-and-model-findings-that-need-a-device-asm-depth-pass-task-5d).
- The ota-record upload (`ota_upgrade_record_reporter.dart`) and the sub-package channel `akiot.device.get_sub_version_list`, which belong to the update itself. — traced 2026-10-20: not traced in this pass; separate subject (the upload happens after the update and is not part of the monitor).

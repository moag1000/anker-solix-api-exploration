# A17B1 MQTT messages

Home Power Panel (A17B1): its status arrives as JSON inside the `a2` field of the messages 0500, 0502, 0503 and 0505 (not as 0405 TLV), and the app decodes it with the model `A17b1MqttDeviceInfoModel`. The envelope, topics and the frame layout are owned by [envelope.md](envelope.md) and not repeated here. The A17B1 has no SET opcode in the audit.

Evidence rows are written `audit row N` and refer to [../docs/audit/BLE_COMMAND_MAP.md](../docs/audit/BLE_COMMAND_MAP.md); `file.dart @0xADDR` is 3.24.3 asm. Model files: `charging/model/a17b1/a17b1_mqtt_device_info_model/{a17b1_mqtt_device_info_model,data_flow,bd}.dart`. JSON key names are upstream's `_PP_JSON` (`api/mqttmap.py` lines 4015-4107); a name of ours is marked `(no upstream name)`. The key strings of the `toJson` methods were read from the asm for this page because the audit rows 100, 101, 354 cover the class sizes and the field types only.

### 0500 0502 0503 0505 JSON status messages

#### Purpose
Periodic system status of the panel with PV, battery, grid, load and per-device battery data.

#### Upstream name
`"0500"`, `"0502"`, `"0503"`, `"0505"`, each with `a2` holding `json: _PP_JSON` (`mqttmap.py` lines 5807-5826), upstream-confirmed.

#### Command code
Message ids from upstream only; the app side decodes the JSON through the model in the next section. Tag: upstream-confirmed.

#### Direction
device→app. Tag: upstream-confirmed.

#### Topic pattern
[envelope.md](envelope.md#topics): `dt/anker_power/A17B1/<sn>/param_info` (the JSON arrives in the `a2` field of the frame).

The app model carries only a subset, see the next section.

### App reader of the JSON (A17B1DeviceCommands.parseDeviceAllInfo)

#### Purpose
The second app-side reader of the `a2` JSON of the panel: it takes the JSON map and copies keys, with defaults, into the device object. New read 2026-10-20 (the page's earlier Known unknowns about defaults and the key `ep` point here).

#### Upstream name
none (app function); key names are upstream's `_PP_JSON` where they exist.

#### Command code
`A17B1DeviceCommands.parseDeviceAllInfo` @0x3b4c6e0 (size 0x2560, `charging/ble/device/A17B1/a17b1_device_commands.dart`). `A17B1DeviceController._handleResponse` @0x3b483bc (size 0x1cc4) calls it for the opcode type `postA17b1DeviceInfoReq` (index 0x6d, key `0500` in the map of [iot.md](iot.md#frame-decode-and-opcode-dispatch); compare @0x3b48984, call @0x3b48a38). `commonParse` @0x3b4a548 (size 0x1e4) reads the tag `a2` of the frame (`indexString` argument 162 @0x3b4a598), decodes it as UTF-8 and runs `jsonDecode` (@0x3b4a5fc), which confirms that the status JSON is the payload of `a2`; `parseDeviceAllInfo` then reads the key `data` of that map and the keys below from the nested map. The controller has `handleMQTTDeviceResponse` @0x3b47f18, so the message reaches this reader from the MQTT path. Asm-traced.

#### Direction
device→app.

#### Topic pattern
[envelope.md](envelope.md#topics): the `param_info` topic of the A17B1 controller (the same gate as for the other PPS controllers, [iot.md](iot.md#mqtt-receive-path-and-topic-gate)).

#### Payload fields
Keys read, in code order (first reads only; the slot keys `90as`, `90asoc`, `90asn`, `90av` and `90bs`, `90bsoc`, `90bsn`, `90bv` are read twice, once per branch). A default is the value used when the key is absent; integers are Smi values, so a raw immediate is halved (the old doc's 0, 2 and 40 are raw immediates: `m` defaults to 1 and `cp` to 20, `cmp w0,NULL` then `r4 = 2` @0x3b4e498 and `r4 = 40` @0x3b4e3f4, stored with 32-bit stores at offsets 1271 and 1267). `ep` is read with default 0 @0x3b4e2c0.

### A17b1MqttDeviceInfoModel (app model)

#### Purpose
The app-side model that `fromJson`/`toJson` map between the JSON status keys and the fields shown in the app.

#### Upstream name
none (the model name is the app's; key names are upstream's where mapped).

#### Command code
Not a message. `A17b1MqttDeviceInfoModel` has class size 0x74 (`fromJson` @0x24356fc size 0xf98, `toJson` @0x24366dc); the nested `DataFlow` has class size 0x28 and `Bd` size 0x20 (audit rows 354, 100, 101). Asm-traced.

#### Direction
device→app (decoded by `fromJson`); `toJson` is used by the app to serialise.

#### Topic pattern
[envelope.md](envelope.md#topics): same carrier as above.

#### Payload fields
Top-level keys: the 26 `toJson` keys in source order plus `opu`, which only `fromJson` reads (27 keys, matching the 27 slots). Every field is a nullable `int?` in the model; the only integer immediates in `fromJson`/`toJson` are the class-id checks for `int?` (60; audit row 354). `DataFlow` has 8 slots ((0x28 - 8) / 4) and `Bd` has 6 slots ((0x20 - 8) / 4).

# A1780 (F2000, Bluetooth-only) BLE

The SOLIX F2000 / PowerHouse 767 (A1780) without WLAN. This page owns the BLE-specific facts of the product; the command payloads (opcodes, TLV tags, scales) are owned by the MQTT page [../mqtt/a1780.md](../mqtt/a1780.md) and are not repeated here. The frame, fragmentation and encryption are on [protocol.md](protocol.md), the negotiation on [handshake.md](handshake.md).

Evidence is the asm of 3.24.3 (`file.dart @0xADDR`, relative to `charging/ble/device/` unless a path is given). Pool lists such as `[0, 0x5e]` are real values. A row that says `no` in the column `on the MQTT page` means the opcode is not mentioned on the linked page; it can still be a command that also goes over MQTT.

Notes on this product:

- `A1780AnkerDevice` does not mix in `ZXBleFeature` (no handshake method of the ZX set in the class) and the product uses the legacy GATT group with the literal characteristic ids `7777` and `8888`. The ZX handshake of [handshake.md](handshake.md) is not available through this class.
- `A1780Commands` (`a1780_commands.dart`) holds the positional parser (`parseOtherData`, `parseSwitchData`, `parseCountdownData`, `parseDeviceInfo`), documented with the audit's corrected windows on [../mqtt/a1780.md](../mqtt/a1780.md); `A5140Commands` reuses the same file name (`a1780_commands.dart` in the A5140 directory).
- Session setup, app side: `A1780AnkerDevice` (class id 8456) has no `ZXBleFeature` in its `extends` line; its class id is outside the ids that `ZXBleConfer.sendConnectCommand` accepts, so the Dart conferers send no start-connect request for it ([handshake.md](handshake.md#which-implementation-runs-for-a-product)). `A1780` is not a registered SDK product code, so `BleHandler` picks `BleHandlerImpl1`; `_authDevice` still calls `startZXBleConfer`. The legacy connect path (`SimpleBleConnector._connectLegacyDevice`) is not linked from this class: `SimpleBleConnector.connect` has a single caller in the asm, in the A7320 unbind flow ([protocol.md](protocol.md#stacks-and-send-routing)). The connect call for this product: `ui/page/device/a1780/a1780home/a1780home_logic.dart @0x2667b50` and `.../a1780ota/a1780ota_logic.dart @0x4172e08` call `BleHandler.startScanWithConnect`. No negotiation step for this class is visible in the asm.

## Commands

### Device-class methods

#### Purpose

Records that this device class has no ZX handshake method; the session setup of the product is not the ZX negotiation of [handshake.md](handshake.md).

#### Upstream name

none for the sequence; the opcode names are the app's `ZXOpcodeType` members (no upstream name).

#### Opcode

No pool opcode list in `a1780_anker_device.dart`: the class defines no opcode methods and does not mix in `ZXBleFeature`.

#### Direction

both: requests go app to device, the responses (`08xx` in the common map, [handshake.md](handshake.md#opcode-pairs)) come back device to app.

#### Packet framing

[protocol.md](protocol.md#frame-on-ble); the handshake frames carry the flag bits of [protocol.md](protocol.md#opcode-byte-0-flags).

#### Handshake prerequisite

The rows of group `handshake` are the handshake. Which conferer runs (`SecureEcdhConfer`, `EcdhConfer` or `AesConferV1`) is chosen from the capability response, not from the product: [handshake.md](handshake.md#capability-negotiation-response). The other rows are ordinary commands that need a completed handshake for encrypted frames.

#### TLV tags

The handshake payloads are positional bytes or single tags and are not per-product; they are described in [handshake.md](handshake.md#capability-negotiation-response) and [handshake.md](handshake.md#the-three-conferers). The payloads of the WiFi, OTA and status-request rows were not decoded for this page.

#### Example

none: no capture of a handshake exists in this repository.

#### Related API endpoint

MQTT twin and device page: [../mqtt/a1780.md](../mqtt/a1780.md). The handshake itself has no MQTT twin.

#### Since/changed

3.18.0: the same device-class files. 3.24.3: the opcode set of the device-class file(s) is unchanged; the `ProductModel` of A1780 existed in 3.18.0 (see [protocol.md](protocol.md#since-3180)).

#### Known unknowns

none.

BLE is unavailable while the device is on WiFi; see `ble/protocol.md` (community finding, see protocol.md; not asm-traced).

#### Device-tested by

none.

#### Known unknowns

- Rows marked `no` may be commands that are MQTT-only on the cloud side or simply undocumented on the MQTT page; this page does not decide which.
- The send set of `A1780DeviceController`, which the table above does not list: its methods send static byte lists of `A1780Commands` (21 static fields, `a1780_commands.dart`; for example the field at offset `0x2174` loaded at `a1780_device_controller.dart @0x33f12c8`) through `_sendCommandWithParams` (`@0x33f105c`); payload tags and response handling of these methods were not decoded. — traced 2026-10-20: the controller has 22 `LoadStaticField(0x2...)` sites; the lists and their methods were not tabulated.

BLE is unavailable while the device is on WiFi; see `ble/protocol.md` (community finding, see protocol.md; not asm-traced).
